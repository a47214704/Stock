# 「純前端接資料」可行性評估

評估「不寫後端，瀏覽器直接打交易所 API 做分析」這個做法。

**結論：全市場選股不可行；單檔個股分析可行。但有一個折衷方案能同時滿足「不維護伺服器」和「全市場選股」。**

---

## 一、三個擋路的問題（依嚴重度排序）

### 1. 外資庫存無法累積 —— 致命，且與 CORS 無關

`MI_QFIIS`（外資持股）**官方只提供當日快照，沒有歷史查詢端點**。

要判斷「外資庫存 3 個月持續增加」，唯一方法是每個交易日抓一次、自己存起來，累積成時間序列。純前端沒有持久化的地方：

- `localStorage` 理論上可存，但前提是**使用者必須連續 3 個月、每個交易日都打開這個網頁**。漏掉幾天資料就斷，換裝置、換瀏覽器、清快取就全沒了。
- 新使用者第一次打開網站，看到的是空的，而且要等三個月才有東西可看。

這一條讓「純前端」在條件 3b 上結構性地做不到。**就算 CORS 全開、請求無上限，這個問題依然存在。**

### 2. 全市場掃描的請求量

`STOCK_DAY` 一次只回傳單一個股的單一月份。全市場約 1,800 檔、回補 6 個月：

```
1,800 檔 × 6 個月            = 10,800 次   （日 K）
+ 融資 / 外資持股 / 三大法人   ≈ 每日 3 次 × 120 天 = 360 次（全市場報表，這部分還好）
```

日 K 的一萬多次請求，要在使用者打開網頁後於瀏覽器內跑完，不切實際。而且：

- 交易所公開 API 沒有正式使用授權，流量大會限速／擋 IP。
- 純前端的架構下，**去打交易所的是每一個使用者自己的瀏覽器**。使用者一多，被 ban 的是使用者家裡的 IP，你完全無法控管、也無法快取共用。這是比技術限制更麻煩的地方。

### 3. CORS —— 未知，需實測

交易所 API 是否回 `Access-Control-Allow-Origin`，我無法在此環境驗證（對外連線被封鎖），公開資料也沒有明確說法。注意 `openapi.twse.com.tw` 自帶的 Swagger UI 能運作**不能當作證據** —— 那是同源請求。

自己測最快，在任意網頁的 DevTools Console 貼上：

```js
fetch('https://openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL')
  .then(r => r.json()).then(d => console.log('OK', d.length))
  .catch(e => console.error('BLOCKED', e));
```

`www.twse.com.tw/rwd/...`（T86、MI_MARGN、MI_QFIIS 都在這個網域）要另外測一次，兩個網域的設定不一定相同。

即使測出來是通的，也只是解除了問題 3，問題 1 和 2 依然無解。

### 附帶：FinMind token 會曝光

若改用 FinMind，token 寫在前端等於公開。任何人都能從 Network 分頁撈走，拿去耗用你的額度。

## 二、推薦方案：GitHub Actions + 靜態 JSON

這個做法保留了「純前端」的全部好處 —— **零伺服器、零維運、零費用、前端 100% 靜態** —— 同時解決上面三個問題。

```
GitHub Actions（每交易日 15:00 排程）
    ↓ 跑 ETL 抓 TWSE / TPEx
    ↓ 計算季線扣抵、MACD、盤整區間、籌碼趨勢
    ↓ 產出 JSON，commit 回 repo
GitHub Pages / Cloudflare Pages（靜態託管）
    ↓
前端 fetch 同源的 signals.json → 渲染
```

為什麼這個做法成立：

| 問題 | 如何解決 |
|---|---|
| 外資庫存無法累積 | 每日 commit 進 git，**git history 就是你的時間序列資料庫**，永久保存且不依賴使用者行為 |
| 請求量 / 被 ban | 抓取集中在 GitHub 的機器、一天一次；使用者的瀏覽器完全不碰交易所 |
| CORS | JSON 與網頁同源，不存在跨域問題 |
| token 曝光 | 放 GitHub Secrets，只在 Actions 內使用，不進前端 |

資料量也很合理：

- `signals.json`（全市場每檔最新指標與篩選結果）：1,800 檔 × 約 200 bytes ≈ 360 KB，gzip 後約 60 KB，一次載入沒問題。
- 個股日 K 明細：切成 `data/2330.json` 之類的檔案，使用者點開哪檔才 lazy load 哪檔。

要注意的兩點：

- **repo 體積**：每日 commit 會持續長大，但實測是可控的。做法是每日快照
  一天一個檔、寫入後不再改動（git 每天只新增一個 blob，不重寫既有檔案），
  並採欄位化編碼讓欄位名只出現一次。以 1800 檔實測：每日原始 240 KB、
  git 壓縮後 105 KB，一年約 26 MB，五年約 128 MB。若日後想再壓，
  可把兩年前的快照合併成年度檔案封存。
- **排程會被停用**：public repo 的 GitHub Actions 排程若 60 天無任何 commit 活動會自動停用。這個專案每天都有 commit，實務上不會遇到。

進階選項：ETL 直接產出 SQLite 檔，前端用 `sql.js` 或 DuckDB-WASM 載入，就能在瀏覽器內下 SQL 做任意條件組合的篩選，不必事先把所有篩選邏輯寫死在 ETL。

## 三、方案比較

| 方案 | 全市場選股 | 外資庫存趨勢 | 維運成本 | 費用 |
|---|---|---|---|---|
| 純前端直接打交易所 | ✗ 請求量爆炸 | ✗ 無法累積 | 無 | 免費 |
| 純前端 + 公用 CORS proxy | ✗ | ✗ | 無 | 免費但不穩定，公用 proxy 隨時會掛 |
| **GitHub Actions + 靜態 JSON** | **✓** | **✓** | **極低** | **免費** |
| Serverless 代理（Workers / Vercel） | △ 仍受請求量限制 | 需另加 KV/D1 才行 | 低 | 有免費額度 |
| 傳統後端 + PostgreSQL | ✓ | ✓ | 高 | 需付主機費 |

## 四、什麼情況下純前端真的可行

如果需求縮小成「**使用者輸入一檔股票代號，看這一檔的分析結果**」，那純前端是可行的：

- 請求數降到個位數（單檔 6 個月日 K = 6 次，加上當日籌碼報表數次）。
- 條件 1、2、4（盤整、季線扣抵、MACD）只吃收盤價，單檔資料量就夠算。
- 條件 3a、3c（融資趨勢、法人買賣超）能從歷史報表逐日回補，勉強可行但請求數不少。
- **條件 3b（外資庫存趨勢）依然做不到** —— 沒有歷史端點可回補。

前提仍是 CORS 要通。這適合做成 MVP 先驗證選股邏輯對不對，之後再長成完整方案。

## 建議路徑

1. 先花 10 分鐘用上面的 snippet 測 CORS，這決定 MVP 能不能純前端起步。
2. **不論結果如何，立刻建立每日抓 `MI_QFIIS` 的排程並開始存**。外資庫存是唯一有時間壓力的資料 —— 今天不開始存，三個月後才有得分析。
3. 主架構走 GitHub Actions + 靜態 JSON。
